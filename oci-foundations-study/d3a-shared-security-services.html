3.1–3.2 Shared Security Model และ Security Services D3 · 25%

อ่านประมาณ 55–70 นาที · objectives 3.1 (Shared Security Model) และ 3.2 (Security services)

Why it matters

Security เป็นโดเมนน้ำหนัก 25% และเป็นสิ่งที่ "ข้อสอบจริงถามเพื่อแยกคนที่เข้าใจงานจริงออกจากคนท่องชื่อ" — โจทย์มักเล่าสถานการณ์แล้วยื่นบริการ security มาให้เลือก ถ้าจำได้ว่าแต่ละตัวทำหน้าที่อะไร ก็ตอบได้เลย

อุปมา
เช่าคอนโด: เจ้าของอาคาร (Oracle) รับผิดชอบ ตัวอาคาร — โครงสร้าง ประตูหลัก ไฟ ระบบน้ำดับเพลิง นั่นคือ security OF the cloud ส่วนคุณรับผิดชอบ ในห้องของคุณ — ล็อกประตูห้อง เก็บของมีค่า ใครเข้าออกได้บ้าง นั่นคือ security IN the cloud

3.1 Shared Security Model

ความรับผิดชอบOracle ดูแล (security of the cloud)คุณดูแล (security in the cloud)
Physical / Data centerความปลอดภัยของ datacenter, rack, power, network backbone, hypervisor—
Network / HypervisorOracle Cloud Network แยก tenant, off-box virtualizationVCN design, security lists/NSG, route tables
IaaS (เช่น Compute VM)hardware + hypervisorOS, patching, firewall, ข้อมูล, access control ทั้งหมด
PaaS (เช่น Autonomous DB)hardware + OS + database engine + patch อัตโนมัติข้อมูล, สิทธิ์ผู้ใช้ DB, network access ของ DB, การตั้งค่า encryption key
SaaS (เช่น Fusion Apps)เกือบทั้งหมด (infra + app)ข้อมูลที่ป้อนเข้า, user access, การตั้งค่าความปลอดภัยของแอป
หลักจำ
ยิ่งเป็น SaaS ยิ่ง Oracle ดูแลเยอะ ยิ่งเป็น IaaS ยิ่งคุณดูแลเยอะ — แต่ ข้อมูลของคุณเป็นความรับผิดชอบของคุณเสมอ ไม่ว่าโมเดลไหน (รวมถึงการจัดการ access)

หลักการออกแบบ security

  • Defense in Depth — หลายชั้นซ้อนกัน (network → host → app → data) ชั้นใดชั้นหนึ่งแตก ยังมีชั้นอื่นกันต่อ
  • Least Privilege — ให้สิทธิ์น้อยที่สุดที่จำเป็นต้องใช้ และเท่าที่จำเป็นเท่านั้น; ทบทวนสิทธิ์สม่ำเสมอ
  • Zero Trust — ไม่ไว้ใจใครโดยอัตโนมัติ แม้แต่ในเครือข่ายภายใน — verify explicitly, least privilege access, assume breach; บน OCI ใช้ร่วมกับ IAM conditions, Bastion, WAF และ ZTPR

Compliance programs และวิธีเข้าถึงเอกสาร

  • OCI ผ่านการตรวจรับรองระดับสากล เช่น ISO 27001/27017/27018, SOC 1/2/3, PCI-DSS, HIPAA, FedRAMP, GDPR, CSA STAR ฯลฯ (รายการจริงและระดับที่ยืนยันได้ เปลี่ยนได้ — ตรวจสอบกับ Oracle)
  • เอกสาร compliance และรายงาน audit อยู่ที่ Oracle Cloud Infrastructure Trust Center (cloud.oracle.com/iaas/compliance) และใน Console: Governance → Compliance — ลูกค้าที่มี contract เข้าดู/ดาวน์โหลดรายงานได้
  • Data residency — ข้อมูลอยู่ใน region ที่คุณเลือกเสมอ (ไม่ย้ายข้าม region/realm เอง); บางประเทศมีข้อบังคับเฉพาะ (เช่น ข้อมูลส่วนบุคคลในไทย/ยุโรป)

Cloud Guard (ด่านตรวจจับ + ตอบสนอง)

  • Cloud Guard = บริการ detect + respond ภัยคุกคามอัตโนมัติ ทำงานแบบ "detector ตรวจเจอปัญหา → responder แก้ให้อัตโนมัติ"
  • องค์ประกอบหลัก:
    • Target — สิ่งที่ Cloud Guard มอนิเตอร์ (เช่น tenancy หรือ compartment)
    • Recipe — ชุดของ rules สำเร็จรูป (Detector recipe / Responder recipe); เลือกระดับ managed (Oracle อัปเดตให้) หรือ custom
    • Detector rule — กฎตรวจจับ (เช่น "มี bucket public", "มี VCN เปิด 0.0.0.0/0 ไปทุกพอร์ต", "มี user พยายาม MFA ไม่ผ่านหลายครั้ง")
    • Responder rule — การตอบสนองอัตโนมัติ (เช่น "ปิด public bucket อัตโนมัติ", "ตัดสิทธิ์ user", "แจ้งเตือน")
    • Problem — รายการปัญหาที่ตรวจพบ มี severity และสถานะ
  • ทำงานจาก activity logs และ configuration (รวมถึง Audit logs) — มอนิเตอร์แบบต่อเนื่อง
  • แนวทางสอบ: "ตรวจจับการตั้งค่าผิด + แก้อัตโนมัติ" → Cloud Guard; "ป้องกันไม่ให้ตั้งค่าผิดตั้งแต่แรก" → Security Zones

Security Zones (บังคับ posture ตั้งแต่สร้างทรัพยากร)

  • Security Zone = compartment พิเศษที่มี security policies บังคับ ว่าสร้างทรัพยากรแบบไหนได้/ไม่ได้ — ป้องกัน ตั้งแต่ก่อนเกิด (proactive)
  • ตัวอย่างกฎ: ห้ามสร้าง public bucket, ห้ามปิด encryption, ห้ามเปิด security list กว้างเกิน, ห้ามสร้างฐานข้อมูลที่ไม่มี backup — สร้างแล้วขัดกับกฎ = ถูกปฏิเสธทันที
  • ต่างจาก Cloud Guard: Security Zone ป้องกัน ก่อน (preventive), Cloud Guard ตรวจจับ หลัง (detective) — ประกอบกันเป็น defense in depth

Vault — กุญแจและความลับ (Key Management & Secrets)

  • Vault = ที่เก็บ encryption keys และ secrets อย่างปลอดภัย
  • Master Encryption Keys — กุญแจสำหรับเข้ารหัสข้อมูล (เช่น block volume, object storage, database) เลือกชนิด:
    • Software-protected keys — เก็บในซอฟต์แวร์ HSM จำลอง (HSM ระดับซอฟต์แวร์)
    • HSM keys — เก็บใน Hardware Security Module จริง (FIPS 140-2 Level 3) — แข็งแรงกว่า ราคา/ข้อจำกัดมากกว่า
  • Secrets — เก็บรหัสผ่าน, API keys, connection strings; เข้าผ่าน API/CLI; รองรับ versioning ของ secret; ใส่ใน instance ผ่าน instance principals/secrets โดยไม่ hardcode
  • Customer-managed keys (CMK) — คุณเป็นเจ้าของ/จัดการกุญแจเอง (แทนที่จะใช้ Oracle-managed keys) สำหรับ compliance ที่ต้องการควบคุมวงจรชีวิตกุญแจ
  • ถอดกุญแจ = ข้อมูลถอดรหัสไม่ได้ (Cryptographic erasure) ใช้ตอนเลิกใช้ข้อมูลตาม policy

WAF และ DDoS Protection

  • Web Application Firewall (WAF) — ป้องกันเว็บแอปที่ชั้น L7: กัน OWASP Top 10 (SQL injection, XSS), bot management, rate limiting, geo-blocking; แนบได้กับ public Load Balancer; มี rule สำเร็จรูปและ custom rules
  • DDoS Protection — ป้องกัน Distributed Denial of Service ที่ชั้นเครือข่าย; OCI มี always-on DDoS mitigation สำหรับ public endpoints โดยอัตโนมัติ (ไม่ต้องตั้งค่า) + สามารถตรวจการโจมตีผ่าน WAF/Logging

Bastion, Data Safe, Vulnerability Scanning, Certificates

บริการหน้าที่ / เมื่อไหร่ใช้
Bastionทางเข้า managed ไปยัง private subnet — session จำกัดเวลา (เช่น 3 ชั่วโมง), audit ทุก session, ไม่ต้องมี jump box เอง; รองรับ SSH (Linux) และ RDP (Windows)
Data Safeจัดการ security ของ ฐานข้อมูล โดยเฉพาะ: ค้นหา sensitive data, ประเมินสิทธิ์ผู้ใช้ DB, data masking สำหรับ non-production, audit trail ของ DB
Vulnerability Scanningสแกน VM/container images หา CVE ที่รู้อยู่แล้ว — รายงานและแจ้งเตือน แพตช์ตามผล
Certificatesออก/เก็บ/ต่ออายุใบรับรองดิจิทัล (TLS) แบบ managed; ใช้กับ LB/API Gateway
Network Firewallstateful firewall ชั้น L3–L7 จัดการโดย Oracle — IDS/IPS, TLS inspection, วางหน้า subnet

Audit / Logging / Monitoring

  • Audit — บันทึกทุก API call ที่เกิดใน tenancy (ใครทำอะไร เมื่อไหร่ จากที่ไหน) เก็บใน Logging service โดยอัตโนมัติ — พระเอกของ forensic/compliance
  • Logging — ศูนย์รวม log (service logs + custom logs) — ค้น, สำรอง, ตั้ง alarm ได้
  • Monitoring — metrics ทุกบริการ + alarms (เช่น CPU > 80% นาน 5 นาที → trigger notification) และ dashboards
  • Events + Notifications — automation เมื่อเกิดเหตุการณ์ (เช่น bucket ถูกเขียน → เรียก Functions)

Encryption — at rest และ in transit

  • At rest — ข้อมูลทุกอย่างเข้ารหัส AES-256 เป็นค่า default (block/boot volume, object, database, backups) โดยไม่ต้องตั้งค่า; เลือกใช้ customer-managed keys ผ่าน Vault ได้
  • In transit — ทราฟฟิกระหว่างลูกค้า↔OCI และระหว่าง AD/region เข้ารหัส TLS/เส้นทาง backbone เสมอ; OCI บล็อก plaintext ของ data plane ไม่ให้วิ่งบนเน็ตสาธารณะโดยไม่เข้ารหัส

ตารางเปรียบเทียบบริการที่สับสนบ่อย

บริการทำหน้าที่จังหวะตอบโจทย์แบบ
Security Zonesบังคับนโยบายตั้งแต่สร้างทรัพยากรป้องกันก่อน (proactive)"ห้ามสร้าง public bucket เลย"
Cloud Guardตรวจจับการตั้งค่า/พฤติกรรมผิดปกติ + แก้อัตโนมัติตรวจจับหลัง (reactive)"มีใครเปิด bucket สาธารณะ — ปิดให้อัตโนมัติ"
Data Safeความปลอดภัยของฐานข้อมูล (mask, audit, assess)ทั้งก่อนและหลัง"ปิดบังข้อมูลจริงใน DB ตอนเอาไปเทส"
Vulnerability Scanningสแกน CVE บน host/imagesตามรอบ"image นี้มีช่องโหว่ที่รู้แล้วไหม"
WAFกันการโจมตีเว็บที่ L7 real-time"กัน SQL injection ที่หน้า login"
Bastionทางเข้า private subnet แบบมี auditreal-time (session)"SSH เข้าเครื่องใน private subnet อย่างปลอดภัย"
Vaultเก็บกุญแจและความลับ—"เก็บ DB password / encryption key ที่ไหนดี"

Exam Focus

ข้อสอบชอบถาม
  • ใครรับผิดชอบอะไร: IaaS แล้วลูกค้าดูแล OS; SaaS แล้ว Oracle ดูแลเกือบหมด; ข้อมูลของลูกค้า = ลูกค้าดูแลเสมอ
  • "ตรวจจับ + ตอบสนองอัตโนมัติ" = Cloud Guard; "ห้ามสร้างสิ่งผิดตั้งแต่แรก" = Security Zones; "ฐานข้อมูล: masking/audit" = Data Safe
  • เก็บ encryption keys ใน Vault; ต้องการ FIPS 140-2 Level 3 → HSM keys; ทั่วไป → software keys
  • "SSH เข้า private subnet โดยไม่เปิด port 22 สาธารณะ + audit ครบ" → Bastion
  • "ป้องกัน DDoS" → มี built-in always-on; เว็บที่ต้องการ rule ละเอียด → WAF
  • Audit logs บันทึก API calls ทุกตัวอัตโนมัติ → ใช้เป็นหลักฐาน/forensic
  • การเข้ารหัส at rest เป็น default ไม่ต้องเปิดเอง

Common Traps

กับดัก
  • "Cloud Guard ป้องกันก่อนสร้างทรัพยากร" — ไม่: Cloud Guard ตรวจจับหลังจากมีอยู่แล้ว (detective); preventive คือ Security Zones
  • "Data Safe = Cloud Guard สำหรับ DB" — ครึ่งเดียว: Data Safe โฟกัสข้อมูล/สิทธิ์/audit ในฐานข้อมูลโดยเฉพาะ ไม่ใช่ config ของ cloud ทั่วไป
  • "Vault เก็บ certificate ของเว็บ" — ใบรับรอง TLS อยู่ที่ Certificates service; Vault เก็บ encryption keys และ secrets
  • "ลูกค้าไม่ต้องทำอะไรเลยกับ SaaS" — ยังต้องจัดการ user access และข้อมูลของตัวเอง
  • "WAF กันได้ทุกอย่าง" — WAF กัน L7 web attacks; ไม่ใช่ firewall เครือข่าย (Network Firewall) ไม่ใช่ DDoS (always-on mitigation)
  • "Audit ต้องเปิดเอง" — ไม่: Audit เก็บอัตโนมัติสำหรับทุก API call; แค่ดูได้ใน Logging

Scenario

Scenario 1
ฝ่ายความปลอดภัยอยากได้ระบบที่ "ถ้ามีใครเผลอสร้าง bucket public ใน tenancy ให้ปิดให้ทันทีและแจ้งเตือน security team" — ใช้อะไร?
วิธีคิด: คีย์ = detect + ตอบสนองอัตโนมัติ → Cloud Guard (detector rule หา public bucket + responder rule ปิดให้อัตโนมัติ) ไม่ใช่ Security Zones (กันตั้งแต่สร้าง) — ใช้สองอย่างคู่กันได้แต่คำตอบเดี่ยวคือ Cloud Guard
Scenario 2
ทีม dev ต้องการสำเนาฐานข้อมูล production ไปทดสอบ โดยห้ามมีข้อมูลจริงของลูกค้าปนไป — ใช้บริการใด?
วิธีคิด: คีย์ = ข้อมูลจริงต้องถูกปิดบังใน non-production → Data Safe (data masking) ไม่ใช่ Vault (กุญแจ) ไม่ใช่ Cloud Guard (ตรวจ config)

Check yourself

คุณ (ลูกค้า) — Oracle ดูแลแค่ hardware/hypervisor; OS, patch, firewall, ข้อมูล เป็นของคุณ
Cloud Guard — detector rule ตรวจพบ + responder rule แก้อัตโนมัติ
Security Zones — บังคับ posture ก่อนสร้างทรัพยากร; สร้างผิดกฎจะถูกปฏิเสธ
HSM keys (hardware security module) — แข็งแรงกว่า software-protected keys
Audit service → เก็บใน Logging service — ค้นย้อนหลังได้โดยไม่ต้องตั้งค่าเพิ่ม
