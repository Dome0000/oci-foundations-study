D1 · Getting Started with OCI D1 · 15%

อ่านประมาณ 40–50 นาที · objectives 1.1 (OCI Distributed Cloud) และ 1.2 (Regions & Availability Domains)

Why it matters

Domain 1 เป็นด่านแรกของข้อสอบ — คำถามส่วนใหญ่เป็น recall (ข้อเท็จจริงตรง ๆ) ถ้าแม่นตรงนี้ได้ ~6 ข้อฟรี ๆ นอกจากนี้แนวคิด regions/ADs ยังใช้ตอบโดเมนอื่นอีกหลายข้อ (เช่น "resource นี้ย้ายข้าม region ได้ไหม")

อุปมา
OCI คือเครือข่ายธนาคารสาขา: Realm = กลุ่มประเทศที่ธนาคารมีสาขา · Region = สาขาในประเทศนั้น · Availability Domain = ตึกคนละตึกในเมืองเดียวกัน (ไฟดับตึกหนึ่ง อีกตึกยังเปิด) · Fault Domain = ชั้นคนละชั้นในตึกเดียวกัน (ชั้นหนึ่งเครื่องดับ ชั้นอื่นยังทำงาน)

พื้นฐาน Cloud ที่ต้องรู้

IaaS / PaaS / SaaS

โมเดลคุณจัดการอะไรตัวอย่างบน OCI
IaaS (Infrastructure as a Service)OS, runtime, แอป, ข้อมูล — ได้แค่ hardware เสมือน (VM/network/storage)Compute VM, Block Volume, VCN
PaaS (Platform as a Service)แค่แอปและข้อมูล — แพลตฟอร์ม/runtime จัดการให้Autonomous Database, Functions, OKE
SaaS (Software as a Service)แค่ใช้แอป ไม่ต้องจัดการอะไรเลยOracle Fusion Cloud Applications (ERP/HCM)

CapEx vs OpEx

  • CapEx (Capital Expenditure) — ลงทุนก้อนใหญ่ซื้อเครื่อง/data center ล่วงหน้า ทรัพย์สินเก่าลงเรื่อย ๆ; เหมาะกับ on-premises แบบเดิม
  • OpEx (Operational Expenditure) — จ่ายเท่าที่ใช้จริงรายเดือน ไม่ต้องซื้อล่วงหน้า; cloud ส่วนใหญ่เป็น OpEx — เหตุผลหลักที่ธุรกิจย้ายขึ้น cloud

Elasticity vs Scalability

  • Scalability — ระบบขยายขนาดรองรับงานมากขึ้นได้ (ทั้ง scale-up แนวตั้ง และ scale-out แนวนอน) อาจทำทันทีหรือวางแผนล่วงหน้า
  • Elasticity — ขยาย/หดแบบ อัตโนมัติตามความต้องการจริงแบบ real-time แล้วจ่ายตามที่ใช้ — elasticity คือ scalability แบบอัตโนมัติและยืดหยุ่นทั้งสองทาง

High Availability (HA) vs Disaster Recovery (DR)

HADR
เป้าหมายลด downtime จากความล้มเหลวเล็ก ๆ (instance ดับ, rack เสีย)กู้ระบบจากเหตุใหญ่ (region หาย, data center พัง)
เครื่องมือหลาย AD + Load Balancer + instance poolสำรองข้าม region (backup, replication, standby)
ตัวชี้วัดuptime %RTO (Recovery Time Objective — กู้กลับมาใช้ได้ภายในกี่นาที/ชม.) และ RPO (Recovery Point Objective — ยอมเสียข้อมูลย้อนหลังกี่นาที/ชม.)

1.1 OCI Distributed Cloud (คลาวด์แบบกระจายตัว)

Distributed Cloud = Oracle นำ OCI ไปรัน ๆ ทุกที่ที่ลูกค้าต้องการ — ไม่ใช่แค่ public cloud ใน region ของ Oracle แต่รวมถึงที่ลูกค้าตั้งเอง พันธมิตรรันให้ และ multicloud ด้วย OCI เป็น cloud เดียวที่มาตรฐานเดียวกัน ทุกรูปแบบ (บริการเดียวกัน ราคาใกล้เคียงกัน จัดการจาก Console อันเดียวกัน)

รูปแบบคืออะไร / เมื่อไหร่ใช้
Public Cloud (region ของ Oracle)OCI ใน region สาธารณะของ Oracle ทั่วโลก — ตัวเลือกมาตรฐาน ราคาถูกที่สุด ใช้ได้ทันที เหมาะกับ workload ทั่วไป
Dedicated Region Cloud@CustomerOracle ติดตั้ง region เต็มรูปแบบของ OCI ไว้ใน datacenter ของลูกค้า — ได้บริการครบเหมือน public cloud แต่ข้อมูลอยู่ในมือลูกค้า เหมาะกับข้อกำหนด data residency/ระเบียบเข้มงวด
Oracle Alloyคู่ค้า/พันธมิตร (เช่น service provider) ซื้อสิทธิ์รัน OCI ภายใต้แบรนด์ของตัวเอง แล้วขายต่อ/ให้บริการลูกค้าของตน — cloud ส่วนตัวของ partner ที่ขับเคลื่อนด้วย OCI
Oracle AI Database@Azure / @AWS / @Google Cloud (ชื่อเดิม Oracle Database@...)Oracle Database รันบน infrastructure ของ Azure / AWS / Google Cloud โดยตรง (multicloud) — ลูกค้าใช้ database ของ Oracle ใน cloud ที่องค์กรใช้อยู่ โดยไม่ต้องย้าย workload ทั้งหมด
Oracle Interconnect for Azure / AWS / Google Cloudลิงก์ส่วนตัว latency ต่ำระหว่าง OCI กับ multicloud เจ้าอื่น ให้แอปข้าม cloud ได้เร็วเหมือนอยู่ในเครือข่ายเดียวกัน
Sovereign / Government Cloudregion สำหรับภาครัฐและข้อมูลอ่อนไหว (เช่น US Government, EU sovereign) — บุคลากรที่มีภูมิหลังตรวจสอบ (cleared) และการันตีว่าข้อมูลไม่ออกนอกประเทศ/เขตอำนาจศาล
Compute Cloud@Customer / Base Database Cloud@Customer / Exadata Cloud@CustomerOCI บางบริการ (compute, database) ติดตั้งที่ลูกค้า — เล็กกว่า Dedicated Region (ที่ยกทั้ง region มา)
Private Cloud ApplianceAppliance สำเร็จรูปขนาดเล็กติดตั้งที่ลูกค้า สำหรับ on-premises cloud ขนาดย่อม
Roving Edge Infrastructureอุปกรณ์ edge พกพา รัน compute/storage แบบ offline ได้ เหมาะกับเรือ เหมือง remote site งานสนาม

ทำไม OCI ถึงเน้น "distributed"

  • Gen 2 architecture — OCI ออกแบบใหม่ทั้งหมด (ไม่ใช่รุ่นต่อยอดจากระบบเก่า) แยก network off-box, ใช้ RDMA network ระหว่างเซิร์ฟเวอร์, isolating tenant ด้วย hardware virtualization ที่ปลอดภัยกว่า
  • ราคาและบริการสม่ำเสมอทุกรูปแบบ — ตัวไหนดก็ API เดียวกัน เครื่องมือเดียวกัน ราคาใกล้เคียงกัน (ยกเว้นต้นทุน delivery เฉพาะรุ่น)
  • Security-first — ทุกการออกแบบมี security เป็นตัวตั้ง (เข้ารหัส default, isolation เข้มงวด)
  • ไม่ต้องเลือกอย่างใดอย่างหนึ่ง — เริ่ม public cloud → ขยายไป dedicated/multicloud เมื่อข้อกำหนดเปลี่ยน

1.2 Realms, Regions, Availability Domains, Fault Domains

นิยามแต่ละระดับ (ตามเอกสารทางการ)

ระดับคืออะไรจุดสำคัญ
Realmกลุ่มของ region; tenancy ของคุณอยู่ใน realm เดียว และเข้าได้เฉพาะ region ใน realm นั้นมี commercial (OC1), government และ dedicated realms; realm พิเศษ เช่น Serbia Central อยู่ realm OC20
Regionพื้นที่ทางภูมิศาสตร์ที่มี datacenter อย่างน้อยหนึ่งแห่ง; region หนึ่งประกอบด้วย AD ตั้งแต่ 1 แห่งขึ้นไปแยกจากกันโดยสิ้นเชิง; งานใหม่ ๆ เปิดเป็น single-AD region
Availability Domain (AD)หนึ่งหรือหลาย datacenter ใน region เดียวกัน แยกไฟฟ้า ความเย็น และเครือข่ายภายในจากกันภายใน region เชื่อมกันด้วยเครือข่าย low-latency high-bandwidth → ทำ HA/DR ข้าม AD ได้ดีมาก
Fault Domain (FD)กลุ่มฮาร์ดแวร์ย่อยภายใน AD — ทุก AD มี 3 FD เสมอใส่ instance คนละ FD = ไม่แชร์ฮาร์ดแวร์เดียวกัน (กัน hardware failure + planned maintenance)
  • ชื่อ AD สุ่มต่อ tenancy — PHX-AD-1 ของคุณกับของคนอื่นอาจเป็นคนละตึก (มี prefix ของ tenancy เช่น Uocm:PHX-AD-1) อย่าวางแผนโดยสมมติว่าชื่อตรงกัน
  • Multi-AD region มีเพียงบางregion (เช่น Phoenix, Ashburn, Chicago, London, Frankfurt — 3 ADs); region อื่น ๆ ส่วนใหญ่ single-AD
  • Subscription limit — tenancy แบบ trial/free tier/pay-as-you-go โดยทั่วไป สมัครได้ 1 region (ขอเพิ่มได้); แบบ Universal Credits สมัครได้ทุก commercial region

Resource ไหน regional / AD-specific / global?

ขอบเขตตัวอย่างหมายเหตุ
Global (cross-region)IAM resources ทั้งหมด (users, groups, compartments, policies, dynamic groups, tag namespaces/keys), Cloud Guard configสร้างครั้งเดียว ใช้ได้ทุก region
RegionalVCN, subnets (regional), route tables, security lists, NSGs, gateways (IGW/NAT/SGW/DRG), Load Balancer, Vault, keys/secrets, buckets, images, functions, OKE clusters, reserved public IPs, Bastion, Autonomous DBทุกอย่างนอกเหนือจาก 2 กลุ่มนี้; bucket เป็น regional แต่เรียกข้ามเน็ตได้ผ่าน URL เฉพาะ region
AD-specificCompute instances, block/boot volumes, DB systems (VM/BM), container instances, ephemeral public IPs, subnets แบบ AD-specific (แบบเก่า)ย้ายข้าม AD ต้องผ่าน backup/image แล้วสร้างใหม่
หลักจำเร็ว
"IAM = global · instance/volume/DB = AD · ที่เหลือ = regional" — ข้อสอบออกช้อยส์แนวนี้บ่อยมาก

การเลือก Region และ Home Region

  1. Latency / ความใกล้ผู้ใช้ — วางใกล้ที่ผู้ใช้/ระบบภายในใช้งาน
  2. Data residency / compliance — บางข้อมูลออกนอกประเทศไม่ได้; บางอุตสาหกรรมมีข้อบังคับเขตอำนาจศาล
  3. Service availability — ไม่ใช่ทุกบริการมีในทุก region (บริการใหม่มักเปิดไม่พร้อมกันทุกที่) ตรวจหน้า Service Availability ของแต่ละ region
  4. Cost — ราคา OCI สม่ำเสมอทุก region โดยรวม (ไม่ต้องเลือกถูกเพราะราคา) ต่างตรง free-tier capacity และความพร้อมของ instance types มากกว่า
  5. Realm constraint — tenancy อยู่ realm ไหน สมัครได้เฉพาะ region ใน realm นั้น
  6. Home region — region ที่ tenancy ของคุณถูก provision เป็นที่แรก (Oracle เลือก/กำหนดตอนสมัคร)
    [ตรวจสอบกับเอกสารทางการ]
    เอกสารปัจจุบันที่ใช้สร้างเนื้อหานี้ไม่ได้ระบุรายละเอียด home region — โดยหลักทั่วไป home region ใช้เก็บข้อมูล identity/global metadata และเปลี่ยนไม่ได้หลังสมัคร ตรวจสอบนิยามล่าสุดกับ Identity documentation ก่อนสอบ

Exam Focus

ข้อสอบชอบถาม
  • "tenancy อยู่ได้หลาย realm ไหม" → ไม่ อยู่ realm เดียว เห็นเฉพาะ region ใน realm นั้น
  • "FD มีกี่อันต่อ AD" → 3 และใช้ป้องกัน hardware failure / planned maintenance
  • "IAM resources เป็น regional หรือ global" → global (cross-region)
  • "region ใหม่ส่วนใหญ่มีกี่ AD" → 1 (multi-AD มีเฉพาะ region ใหญ่บางแห่ง)
  • "AD ชื่อเดียวกันในคนละ tenancy คือตึกเดียวกันไหม" → ไม่ — ชื่อสุ่มต่อ tenancy ต้องเช็คผ่าน Console/API ของตัวเอง
  • "ข้อมูลออกนอกประเทศไม่ได้ ต้องใช้อะไร" → เลือก region ที่ถูกต้อง / Dedicated Region / Sovereign cloud
  • "Oracle Database บน Azure/AWS/Google" → เรียกว่า Oracle AI Database@Azure / @AWS / @Google Cloud (ชื่อเดิม Oracle Database@...)
  • "zone สำหรับภาครัฐ/ข้อมูลลับ" → Government / Sovereign cloud

Common Traps

กับดัก
  • "Region = ประเทศ" — ไม่เสมอไป: region คือ geography ที่ Oracle กำหนด ชื่ออย่าง "ap-singapore-1" อาจไม่ตรงขอบเขตประเทศพอดี
  • "FD ป้องกัน region ล่มได้" — ไม่: FD/AD ป้องกันความล้มเหลวระดับฮาร์ดแวร์/AD; region ล่มต้อง DR ข้าม region
  • "ทุก region มีบริการเหมือนกัน" — ไม่: บางบริการ (โดยเฉพาะใหม่/เฉพาะกลุ่ม) เปิดเฉพาะบาง region
  • "ชื่อ AD ตรงกันทุก tenancy" — ผิด สุ่มต่อ tenancy
  • "Subscribed region ไม่จำกัด" — trial/PAYG โดยทั่วไปจำกัด 1 region (ตรวจสอบ quotas; Universal Credits ไม่จำกัดในเชิงการพาณิชย์)
  • "Distributed cloud = หลาย cloud ผู้ให้บริการคนละเจ้า" — ไม่ครบ: multicloud เป็นส่วนหนึ่งเท่านั้น; Distributed Cloud คือกลยุทธ์ส่งมอบ OCI ทุกรูปแบบสถานที่ (public/dedicated/edge/multicloud) ภายใต้ cloud เดียวกัน

Scenario

Scenario 1
ธนาคารไทยต้องการใช้ OCI แต่นโยบายกำหนดว่าข้อมูลลูกค้าห้ามออกนอกประเทศ แต่ data center ของตัวเองไม่พร้อมสร้าง cloud เอง เลือกอะไรได้บ้าง?
วิธีคิด: ใช้ region ไทย ที่เปิดให้บริการ (commercial region ในประเทศ) เป็นอันดับแรก — ถ้ามีข้อกำหนดเข้มกว่านั้น (ความเป็นอิสระ การควบคุม hardware เต็มรูปแบบ) → Dedicated Region Cloud@Customer ติดตั้งใน datacenter ของธนาคาร; ถ้าเป็นงาน government ที่มี clearance เฉพาะ → sovereign/government region
Scenario 2
ทีมต้องการให้ instance 2 ตัวไม่แชร์ฮาร์ดแวร์เดียวกันภายใน AD เดียวเพื่อกัน planned maintenance พร้อมกัน — ต้องตั้งค่าอะไร?
วิธีคิด: ใส่ใน Fault Domains คนละ FD (FD1/FD2/FD3) ตอนสร้าง instance หรือใน instance pool — ถามต่อว่า "ข้าม AD ล่ะ?" → ต้องวางคนละ AD และใช้ Load Balancer/backup ช่วย

Check yourself

RPO = ยอมเสียข้อมูลย้อนหลังกี่นาที/ชั่วโมง (จุดกู้ข้อมูลล่าสุด); RTO = ยอมให้ระบบล่มนานแค่ไหนก่อนต้องกลับมาใช้ได้
3 อัน — กัน hardware failure และ planned maintenance โดยแยก instance ให้อยู่คนละฮาร์ดแวร์ใน AD เดียวกัน
Dedicated Region Cloud@Customer (Oracle ยก region เต็มไปติดตั้งที่ลูกค้า)
compartment — IAM resources (ซึ่งรวม compartment, users, groups, policies) เป็น cross-region/global ส่วน compute instance และ VCN ไม่ใช่
Scalability = ขยายรองรับงานได้ (อาจทำเอง/อัตโนมัติก็ได้); Elasticity = ขยาย-หด อัตโนมัติตาม demand แบบ real-time และจ่ายตามที่ใช้จริง
