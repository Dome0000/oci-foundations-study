2.3 Storage & Database D2 · 50%

อ่านประมาณ 50–65 นาที · objective 2.3 · หัวข้อ Database เป็นส่วน "เสริม" เพราะไม่ยืนยันว่าอยู่ใน objectives ทางการ

Why it matters

ข้อมูลคือสิ่งที่มีค่าที่สุดบน cloud — การเลือกชนิด storage ผิดทำให้ทั้งแพง ช้า และกู้ข้อมูลไม่ได้ ข้อสอบถาม 3 เรื่องหลัก: (1) Block/Object/File ต่างกันยังไง (2) Object Storage มีฟีเจอร์อะไรบ้าง (versioning/replication/lifecycle/PAR) (3) เมื่อไหร่ควรใช้ database แบบไหน

อุปมา
Block Volume = ฮาร์ดดิสก์ภายนอกที่เสียบกับเครื่องเดียว · Object Storage = โกดังเก็บของที่เรียกผ่าน URL ได้จากที่ไหนก็ได้ · File Storage = ไดรฟ์แชร์ในออฟฟิศ (NFS) ที่หลายเครื่อง mount พร้อมกันได้

Block Volume และ Boot Volume

  • Block Volume — network-attached storage ระดับ block ผูกกับ instance ใน AD เดียวกัน เท่านั้น; ขนาดได้หลาย TB; ทำ snapshot/backup/clone ได้
  • Boot Volume — block volume ที่เก็บ OS ของ instance; เป็น AD-specific เหมือนกัน
  • Performance tiers — Balanced / Higher Performance / Ultra High Performance ปรับได้โดยไม่ต้อง data migration; มี auto-tune ให้ volume ปรับ performance อัตโนมัติตามการใช้งาน
  • Backup — เต็ม (full) หรือ incremental; clone — สำเนาจาก volume/backup โดยไม่ต้อง copy ข้อมูล (metadata copy); Volume Groups — จัดการ backup หลาย volume แบบ consistent พร้อมกัน (เหมาะกับแอป multi-volume)
  • Replication — คัดลอก block volume ไป AD หรือ region อื่นโดยอัตโนมัติ (cross-region backup ก็มี)
  • IOPS/throughput สูงสุดตามขนาดและ tier — อย่าจำตัวเลขตายตัว ตรวจเอกสารปัจจุบัน

Object Storage

โครงสร้าง: Namespace → Bucket → Object

  • Namespace — ตัวระบุระดับบนสุดของทั้ง tenancy: system-generated, ไม่ซ้ำใคร, เปลี่ยนไม่ได้ หนึ่ง tenancy มีหนึ่ง namespace (ชื่อเดียวกันทุก region)
  • Bucket — ที่เก็บ object ภายใน namespace (ชื่อ bucket ต้องไม่ซ้ำใน namespace) เป็น regional resource, ผูก compartment เดียว, default เป็น private
  • Object — ไฟล์ + metadata (custom metadata เป็น key-value, รวมไม่เกิน ~4 KB); ขนาดสูงสุดต่อ object ≈ 10 TiB; อัปโหลดผ่าน API ครั้งละจำกัด (multipart upload สำหรับไฟล์ใหญ่)

Storage tiers (ชั้นการจัดเก็บ)

Tierเหมาะกับเข้าถึง
Standardข้อมูล hot ใช้งานบ่อย (default)ทันที
Infrequent Accessข้อมูลเข้าถึงน้อยแต่ต้องอ่านได้ทันที (เช่น backups, logs 90 วัน)ทันที (ค่า API/retrieval สูงกว่า)
Archiveข้อมูล cold เก็บระยะยาว (compliance)ต้อง restore ก่อน (มี latency) — อ่านตรงไม่ได้

ฟีเจอร์สำคัญที่ข้อสอบถาม

  • Lifecycle policy — กฎย้าย/ลบ object อัตโนมัติ (เช่น "ย้ายไป Archive หลัง 90 วัน, ลบหลัง 2 ปี") — ลดค่าใช้จ่ายโดยไม่ต้องเขียนโค้ด
  • Versioning — เก็บเวอร์ชันเก่าของ object ไว้ กันมือลบ/ทับโดยไม่ตั้งใจ
  • Replication — คัดลอก object จาก bucket ต้นทางไป bucket ปลายทาง (ข้าม region ได้) แบบ asynchronous
  • Pre-Authenticated Request (PAR) — ลิงก์ชั่วคราวให้บุคคลภายนอกอ่าน/เขียน object โดยไม่ต้องมี OCI credentials; มีวันหมดอายุ; ใครถือลิงก์ก็ใช้ได้ — ถือเป็น secret; ลบ PAR = เพิกถอนทันที
  • Retention rules — ล็อก object ไม่ให้ลบ (WORM สำหรับ compliance) แยกจาก lifecycle
  • Encryption — เข้ารหัส at rest เสมอ (AES-256) และ in transit (TLS); รองรับ customer-managed keys ผ่าน Vault
  • เข้าจาก VCN ส่วนตัวผ่าน Service Gateway โดยไม่ผ่านเน็ตสาธารณะ
  • API: REST + Amazon S3-compatible API (ย้าย workload จาก S3 ง่าย) + Swift API
  • Bucket เป็น regional แต่เข้าถึงได้จากที่ใดก็ได้ผ่าน URL เฉพาะ region

File Storage

  • Shared file system แบบ NFS — หลาย instance mount ไฟล์เดียวกันพร้อมกันได้ (read/write) เหมาะกับ content management, home directories, HPC shared data
  • ทรัพยากรหลัก: File system → export ผ่าน mount target (มี private IP ใน subnet) → instance mount ด้วย mount -t nfs ...
  • Snapshot — point-in-time copy แบบ read-only สำหรับ backup/clone
  • เป็น regional (mount target อยู่ใน subnet/AD ตามที่สร้าง แต่ file system เข้าถึงได้ข้าม AD ผ่าน mount target — สร้าง mount target หลาย AD ได้)

บริการย้ายข้อมูลเข้า OCI

  • Data Transfer Service / Data Transfer Appliance — ส่งอุปกรณ์ storage ไปให้ Oracle ยัดข้อมูล (เหมาะกับข้อมูลระดับ PB ที่เน็ตไม่ไหว)
  • rsync / OCI CLI / multipart upload — ย้ายผ่านเครือข่ายสำหรับข้อมูลขนาดเล็กถึงกลาง
  • Database migration — ใช้บริการ Database Migration / Data Pump / GoldenGate สำหรับย้าย database

Decision Tree — เลือก storage ยังไง

ภาพรวม Database บน OCI เสริม — นอกขอบเขตสอบที่ยืนยันไม่ได้

เสริม (นอกขอบเขตสอบ)
หัวข้อ database ไม่ได้ระบุอยู่ใน objectives ของ 1Z0-1085-26 ที่ให้มาใน PROMPT.md และเข้ายืนยันหน้าทางการไม่ได้จากสภาพแวดล้อมนี้ จึงทำเป็น "รู้จักไว้" แบบสั้น — ถ้า objectives ทางการไม่มี ห้ามลงลึก; ถ้ามีให้กลับมาอ่าน docs.oracle.com เพิ่ม
  • Autonomous Database — database จัดการตัวเอง (self-driving/securing/repairing): patch, backup, tune อัตโนมัติ; มีสองรสหลัก: ATP (Autonomous Transaction Processing — OLTP) และ ADW (Autonomous Data Warehouse — analytics); เรียกแบบ serverless หรือ dedicated (Exadata)
  • Base Database Service — Oracle Database บน VM/Bare Metal ที่คุณดูแล (customized), มี Data Guard option
  • Exadata Database Service — Oracle Database บน Exadata infrastructure, performance สูงสุด, มีทั้งแบบ on-cloud และ Cloud@Customer
  • MySQL HeatWave — managed MySQL + HeatWave engine สำหรับ analytics เร็ว; เข้ากับ ecosystem MySQL
  • NoSQL Database — managed NoSQL (key-value/JSON), serverless, latency ต่ำ สำหรับ scale สูง
  • Oracle Database@Azure / @AWS / @Google Cloud — Oracle Database รันใน datacenter ของ Azure/AWS/Google โดยตรง (multicloud) — ดูหน้า D1

Exam Focus

ข้อสอบชอบถาม
  • "หลาย instance ต้องเขียนไฟล์เดียวกันพร้อมกัน" → File Storage (NFS) ไม่ใช่ Block Volume
  • "เก็บ log 5 ปี เรียกดูแทบไม่เคย" → Object Storage Archive tier หรือ lifecycle rule ย้ายอัตโนมัติ — ถ้าต้องอ่านทันทีแต่ไม่ค่อยใช้ → Infrequent Access
  • "ให้ลูกค้าภายนอกอัปโหลดไฟล์โดยไม่มี OCI account" → Pre-Authenticated Request
  • "ป้องกันคนเผลอลบ object เก่า" → versioning; "ป้องกันการลบตามกฎหมาย" → retention rule; "ย้าย/ลบอัตโนมัติตามอายุ" → lifecycle policy
  • Block Volume และ Boot Volume เป็น AD-specific; Object Storage เป็น regional
  • bucket default เป็น private; namespace system-generated เปลี่ยนไม่ได้
  • "เก็บข้อมูลขนาด PB โดยเน็ตไม่ไหว" → Data Transfer Appliance

Common Traps

กับดัก
  • "Archive tier อ่านได้เหมือน Standard" — ผิด: ต้อง restore ก่อน มี restore latency
  • "Block Volume แชร์หลาย instance เขียนพร้อมกันได้" — ผิด: Block ผูกกับ instance ใน AD เดียว เป็นหลัก (การแชร์แบบ multi-attach มีเงื่อนไขพิเศษ); แชร์เขียนพร้อมกันใช้ File Storage
  • "PAR คือ IAM user ชั่วคราว" — ไม่ใช่: PAR คือลายเซ็น URL ไม่เกี่ยวกับ identity; ลบ PAR = เพิกถอน; หมดอายุตามที่ตั้ง
  • "Object Storage ต้องผ่าน public URL เสมอ" — ไม่: private bucket + Service Gateway = ไม่ผ่านเน็ตสาธารณะ
  • "Lifecycle policy ลบ bucket ได้" — ลบได้แค่ objects ใน bucket ไม่ใช่ตัว bucket
  • "Backup ของ Block Volume กู้ข้าม region ไม่ได้เลย" — ทำได้ผ่าน cross-region volume backup/replication (ค่า/เงื่อนไขตรวจเอกสาร)

Scenario

Scenario 1
บริษัทมี log ของแอป 2 TB/วัน ต้องเก็บ 1 ปี โดย 30 วันแรกเข้าดูบ่อย หลังจากนั้นแทบไม่เข้า ออกแบบ storage ยังไงให้ถูกสุด?
วิธีคิด: Object Storage + lifecycle policy: Standard 30 วัน → Infrequent Access หรือ Archive จนครบ 1 ปี → ลบอัตโนมัติ; ไม่ต้องเขียนแอปลบเอง และประหยัดกว่าเก็บ Standard ทั้งปี
Scenario 2
เว็บแอป 3 instance ใน private subnet ต้องให้ upload ไฟล์รูปจากผู้ใช้ขึ้นเก็บที่เดียวกัน และ web tier ทั้งสามอ่านได้พร้อมกัน ตัวเลือกใดเหมาะสุด?
วิธีคิด: ถ้าต้องการแค่ object ผ่าน HTTP → Object Storage (+ PAR ถ้าเป็น direct upload); ถ้าแอปอ่าน/เขียนแบบ filesystem ต้อง mount → File Storage (NFS mount target) — หัวใจคือ "แอปเข้าถึงแบบไหน"

Check yourself

AD-specific — ผูกกับ AD และเข้าถึงได้เฉพาะ instance ใน AD เดียวกัน ข้าม AD ต้องใช้ backup/replication แล้วสร้างใหม่
Pre-Authenticated Request (PAR) — URL ชั่วคราวพร้อมสิทธิ์อ่าน/เขียนที่กำหนด หมดอายุตามเวลา; ลบ PAR เพื่อเพิกถอน
Infrequent Access อ่านได้ทันทีแต่ค่าเข้าถึงสูงกว่า Standard; Archive ต้อง restore ก่อนจึงดาวน์โหลดได้ (มี restore latency) เก็บถูกสุดแต่ไม่เหมาะกับข้อมูลที่ต้องอ่านฉับพลัน
Versioning — เก็บเวอร์ชันเก่าไว้ กู้คืนได้; lifecycle ทำหน้าที่ "ย้าย/ลบอัตโนมัติตามอายุ" ซึ่งเป็นคนละเรื่อง
Autonomous Database — ATP = Transaction Processing (OLTP), ADW = Data Warehouse (analytics); จัดการตัวเองเกือบทั้งหมด
