3.3 Identity and Access Management (IAM) D3 · 25%

อ่านประมาณ 60–75 นาที · objective 3.3 — หัวข้อที่ข้อสอบถามลึกที่สุดของ D3 โดยเฉพาะ policy syntax

Why it matters

IAM คือ "ใครทำอะไรกับอะไรได้บ้าง" — ทุกการกระทำใน OCI ถูกตรวจสอบกับ policy ก่อนเสมอ ข้อสอบชอบให้ policy มาแล้วถามว่า "ใครทำได้/ไม่ได้" ถ้าอ่าน policy ไม่ออกตอบไม่ได้เลย

อุปมา
IAM คือระบบกุญแจของอาคาร: user = คน, group = แผนก, compartment = ห้องแต่ละห้อง (ซ้อนกันได้), policy = ป้ายบนประตูว่า "แผนกบัญชีเข้าได้ห้องเก็บเงิน" · dynamic group = กลุ่มที่สมาชิกเป็น เครื่อง/บริการ ไม่ใช่คน (เช่น "instance ใน compartment นี้ทุกตัวเป็นกลุ่มเดียวกัน")

Tenancy, Compartments, Users, Groups

  • Tenancy — บัญชี/องค์กรระดับบนสุดของคุณใน OCI (ทุกทรัพยากรอยู่ใน tenancy เดียว); สร้างตอนสมัครและใช้ OCID อ้างอิง
  • Compartment — โฟลเดอร์จัดกลุ่มทรัพยากร ซ้อนกันได้ (tree hierarchy) ใช้แยก:
    • ต้นทุน (ดู Cost Analysis แยก compartment)
    • สิทธิ์เข้าถึง (policy ระบุ compartment ได้)
    • quotas และ limits
    ระดับบนสุดคือ root compartment (ชื่อเดียวกับ tenancy); ทุก compartment อยู่ใน root; compartment หนึ่งอยู่ได้ parent เดียว
  • Policies สืบทอดลงล่าง: policy ที่เขียนบน parent compartment ให้สิทธิ์ใน child compartments ทั้งหมด (เหมือน folder permission)
  • User — คนหนึ่งคน (มี credentials, อยู่ใน identity domain)
  • Group — กลุ่มของ users; ให้ policy กับ group ไม่ใช่กับ user รายตัว เพราะจัดการง่ายกว่า
  • Dynamic Group — กลุ่มของ ทรัพยากร (instances, functions, ฯลฯ) ที่ match rule เช่น instance.compartment.id = 'ocid1...' — ให้สิทธิ์กับทรัพยากร โดยไม่ต้องฝัง credential ในโค้ด
  • Network Sources — กำหนดช่วง IP/CIDR ที่อนุญาตให้เข้าถึง (ใช้เป็น condition ใน policy ได้)

Identity Domains, MFA, SSO, Federation

  • Identity Domain — directory แยก logical ภายใน tenancy (เช่น แยก domain ต่อ business unit) เก็บ users/groups/apps; tenancy ใหม่มี default identity domain ให้แล้ว 1 ตัว
  • IAM ปัจจุบันคือ "IAM with identity domains" — รวม identity + federation + OAuth/OIDC ไว้ในตัวเดียว
  • MFA — ผูกกับ user แต่ละคน; บังคับได้ระดับ tenancy/identity domain (แนะนำให้บังคับทุกคน); factor: TOTP app, security key (FIDO2)
  • SSO / Federation — ถ้าองค์กรมี IdP อยู่แล้ว (เช่น Azure AD, Okta, ADFS) เชื่อมผ่าน SAML 2.0 หรือ OpenID Connect (+SCIM สำหรับ provision user อัตโนมัติ) แล้วให้คน sign in ด้วยบัญชีองค์กร ไม่ต้องสร้าง user ใน OCI ซ้ำ
  • Identity Provider (IdP) หนึ่งตัวใช้ token ที่ออกให้ — กำหนด group mapping ระหว่างกลุ่มใน IdP กับกลุ่มใน OCI ได้

Credentials — API Keys และ Auth Tokens

ชนิดใช้ทำอะไรหมายเหตุ
API keys (request signing)เรียก OCI API จาก SDK/CLI — คู่ key (public/private) อัป public key ใน user profileไม่หมดอายุเอง (จัดการเอง); แนะนำ rotation
Auth tokensใช้กับบริการที่ไม่รองรับ API signing (เช่น เข้า Object Storage ผ่าน S3-compatible API, เข้า UI บางอย่าง)เป็น legacy; ใช้กับ S3 API/Swift เป็นหลัก
Customer secret keysS3-compatible access แบบเดียวกับ AWS access keysคู่ access key + secret
OAuth 2.0 tokensสำหรับ apps/clients (เช่น เข้า REST API แทน user)ผ่าน identity domain

Instance Principals และ Resource Principals

  • Instance principals — ให้ compute instance เรียก OCI API แทนตัวมันเอง โดยไม่ต้องฝัง API key ในเครื่อง: instance อยู่ใน dynamic group → dynamic group ได้ policy → instance เรียก API ด้วย identity ของตัวเอง
  • Resource principals — หลักเดียวกัน แต่ใช้กับทรัพยากรอื่น (Functions, Resource Manager, ฯลฯ)
  • เคสคลาสสิก: "instance ต้องอ่าน secrets จาก Vault" → dynamic group ของ instance + policy allow dynamic-group <name> to read secret-family in compartment <x>

Policy Syntax — อ่านให้แตกก่อน

Allow <subject> to <verb> <resource-type> in <location> where <conditions>
ส่วนความหมายตัวอย่าง
subjectใครได้รับสิทธิ์ — group <name>, dynamic-group <name>, any-user, service <name>group DBAdmins
verbระดับสิทธิ์ — ลำดับจากน้อยไปมาก: inspect → read → use → managemanage
resource-typeอะไร — ชื่อ resource family หรือ type เฉพาะ (เช่น instance-family, volume, bucket, object-family, vcn-family, secret-family, database-family)instance-family
locationที่ไหน — tenancy, compartment <name>, compartment id <ocid>compartment Production
where (optional)เงื่อนไขเพิ่มเติม — tag-based, network source, region, request attributewhere request.region = 'ap-singapore-1'

Verbs — จำแค่นี้

Verbทำอะไรได้คิดง่าย ๆ
inspectดู metadata/list ทรัพยากร (ไม่เห็นเนื้อหา)"เห็นว่ามี"
readinspect + ดูเนื้อหา/ค่าจริง (get)"อ่านได้"
useread + ใช้งานทรัพยากร (start/stop, attach, change state) แต่สร้าง/ลบไม่ได้"ใช้เป็น"
manageทุกอย่าง รวม create/update/delete"ทำได้ทุกอย่าง"

Compartment inheritance: policy ที่เขียนบน parent มีผลกับ child compartments ทั้งหมด — เขียนบน root (tenancy) → ครอบทั้ง tenancy

แบบฝึกอ่าน-เขียน Policy (12 ข้อ)

A. อ่าน policy แล้วบอกว่าทำอะไรได้ (1–6)

กลุ่ม Auditors เห็น metadata/list ของทุกทรัพยากรทั้ง tenancy แต่ดูเนื้อหาไม่ได้ (inspect ไม่ใช่ read)
Developers ใช้งาน instance ใน compartment Dev ได้ — start/stop/attach ฯลฯ แต่สร้างหรือลบ instance ไม่ได้ เพราะ use < manage
DBA จัดการฐานข้อมูลทุกอย่างใน compartment Production (สร้าง/แก้/ลบ/backups)
instance/ทรัพยากรใน dynamic group AppServers อ่าน Vault secrets ใน compartment Prod ได้ — ใช้ตอนแอปต้องดึงรหัสผ่าน DB โดยไม่ฝังในโค้ด
NetOps จัดการ VCN ทั้ง tenancy ได้ แต่เฉพาะ region ap-singapore-1 — เงื่อนไข where จำกัด region
Interns อ่าน metadata+เนื้อหา object ใน bucket ชื่อ Staging_bucket ได้ แต่เขียน/ลบ/สร้างไม่ได้

B. เขียน policy ให้โจทย์ (7–12)

Allow group BackupAdmins to manage volume-family in compartment Production (volume-family รวม backup) — ถ้าต้องการเจาะจง: manage volume-backup-family ก็ได้ขึ้นกับ resource-type ที่มีในปัจจุบัน
Allow dynamic-group CICD to manage cluster-family in tenancy — หรือจำกัด compartment ตามที่ pipeline deploy จริง
สิทธิ์อ่าน cost reports: Allow group Finance to read usage-report in tenancy — ตรวจ resource-type ปัจจุบันใน docs (cost/usage reports)
Allow group SecOps to manage security-lists in tenancy where request.networkSource.name='corpnet'
OCI ไม่มี verb "create-without-delete" แยก — ใช้ use instance-family (ใช้ได้แต่สร้างไม่ได้) หรือใช้ manage + จำกัด delete ด้วย condition เช่น where request.permission != 'INSTANCE_DELETE' (ถ้ามี permission นั้นในเอกสารปัจจุบัน — ตรวจสอบ verb/condition ที่รองรับก่อนใช้จริง)
Allow group Auditors to inspect all-resources in tenancy

Conditions (where) — ตัวอย่างที่พบบ่อย

  • request.region = '<region-name>' — จำกัด region
  • request.networkSource.name = '<name>' — จำกัดแหล่งเครือข่าย
  • target.resource.id = '<ocid>' — จำกัดเฉพาะทรัพยากรตัวเดียว
  • request.permission = '<PERMISSION_NAME>' — จำกัด permission เฉพาะตัว
  • target.compartment.id = '<ocid>' — จำกัด compartment เป้าหมาย
  • Tag-based: target.resource.tag.<namespace>.<key> = '<value>' — ให้สิทธิ์เฉพาะทรัพยากรที่ติด tag ตรงเงื่อนไข (ใช้ defined tags)

Tags — Free-form และ Defined

  • Free-form tags — คีย์-ค่าวางเองอิสระ (เช่น team=platform) ง่าย แต่อย่านำไปใช้กับ policy/cost allocation ถ้าต้องการมาตรฐาน
  • Defined tags — ประกาศใน tag namespace ก่อน (เช่น namespace Operations, key CostCenter) — มี type (string/list) ใช้ใน policy conditions และ cost allocation/showback ได้ถูกต้อง
  • Tag defaults — ตั้งให้ทรัพยากรใน compartment ติด tag อัตโนมัติตอนสร้าง (เช่น cost-tracking tag)
  • Cost-tracking tags — tag ที่ใช้แยกต้นทุนใน Cost Analysis / Budgets (ดูหน้า D4)

Exam Focus

ข้อสอบชอบถาม
  • อ่าน policy แล้วตอบ "ทำอะไรได้บ้าง" — ดู subject + verb + resource-type + location ทีละชิ้น
  • manage > use > read > inspect — manage รวม create/delete ด้วย
  • policy ที่ parent compartment มีผลกับ child compartments
  • instance ต้องเรียก OCI API โดยไม่มี key → instance principals + dynamic group + policy
  • ให้สิทธิ์กับ "กลุ่ม" เสมอ ไม่ใช่รายคน
  • cost-tracking / policy ที่ต้องการมาตรฐาน → defined tags; ใช้ใน where → defined tags เท่านั้น
  • federation: SAML 2.0 / OIDC + SCIM; ผู้ใช้ sign in ด้วย IdP องค์กร

Common Traps

กับดัก
  • "แจก manage ให้ทุกคนเพราะขี้เกียจ" — ผิดหลัก least privilege; ใช้ verb ต่ำสุดที่ทำงานได้
  • "policy ต้องเขียนใน compartment ที่จะใช้ทรัพยากร" — ไม่: เขียนที่ไหนก็ได้ที่เข้าถึง compartment ปลายทางได้; ผลของ policy ขยายลง child ได้
  • "dynamic group = กลุ่ม user พิเศษ" — ไม่: dynamic group คือกลุ่มของ ทรัพยากร (instance/function) ไม่ใช่คน
  • "instance principals คือการฝัง API key" — ตรงข้าม: คือการ เลิกฝัง API key โดยใช้ identity ของ instance
  • "free-form tags ใช้ใน policy condition ได้" — ไม่: policy conditions ใช้ defined tags เท่านั้น
  • "read กับ inspect เหมือนกัน" — inspect เห็นแค่ metadata/list; read เห็นเนื้อหาด้วย
  • "root compartment policy ไม่สืบทอด" — สืบทอดทั้ง tenancy

Scenario

Scenario 1
ทีม platform ต้องการให้ทุก instance ใน compartment Apps อ่านรหัสผ่านฐานข้อมูลจาก Vault ได้โดยไม่ฝังในโค้ด เขียน policy อย่างไร?
วิธีคิด: (1) สร้าง dynamic group เช่น instance.compartment.id = '<ocid ของ Apps>' (2) เขียน Allow dynamic-group AppInstances to read secret-family in compartment Apps — ไม่ต้องสร้าง user/api key ใด ๆ เพิ่ม
Scenario 2
ผู้ตรวจบัญชีภายนอกต้องเข้า Console ดูว่ามีทรัพยากรอะไรบ้างในทุก compartment โดยห้ามเห็นข้อมูลจริงและห้ามแก้ไขใด ๆ — ออกแบบ IAM?
วิธีคิด: สร้าง user ให้ auditor (หรือ federate ผ่าน IdP), ใส่กลุ่ม Auditors, เขียน Allow group Auditors to inspect all-resources in tenancy — inspect = เห็น metadata/list เท่านั้น ไม่เห็นเนื้อหา แก้ไขไม่ได้
